# 房车露营营地地图 · 技术架构

## 一、整体定位

一个**众包 POI（兴趣点）+ 会员订阅**的地图应用。核心资产是营地数据，技术只是承载数据的容器。

```
用户 A 标记营地 ──┐
用户 B 标记营地 ──┼──> 审核 ──> 营地数据库 ──> 地图展示 ──> 免费用户：只能看到点位
用户 C 核实评价 ──┘                                    └──> 会员用户：看到完整联系方式
```

商业模式的技术落点只有一个：**同一个接口，按用户等级返回不同字段**。这个判断发生在 `serialize_spot()` 一个函数里。

## 二、技术选型与理由

| 层 | 选型 | 为什么 |
|---|---|---|
| 底图 | OSM 系瓦片（可切换，默认 OpenStreetMap） | 境外 / 国际源，WGS-84。前端按底图坐标系自动换算标记点，见「坐标系跟随」 |
| 前端 | Leaflet + markercluster | 30KB，移动端流畅，插件生态够用。不用 Mapbox 是因为按量计费 |
| 后端 | FastAPI + SQLite + 纯 SQL | 读写比约 100:1，瓶颈在读。SQLite 单文件可扛几十万 POI，省运维 |
| 鉴权 | Bearer Token + PBKDF2 | 无需引入 JWT 库；生产建议换 Argon2 |
| 支付 | 预留订单表 + 回调接口 | 生产接微信支付/支付宝，**必须由服务端回调开通，绝不信任前端** |

**为什么不一开始就上分布式**：这套系统日均 1 万 UV、10 万次瓦片请求、5 万次 API 请求，
一台 2 核 4G 云服务器足够。真正吃资源的是瓦片流量，而瓦片已由底图服务商承担。

### 坐标系跟随（换底图不换数据的做法）

数据库统一存 GCJ-02，前端渲染时按当前底图的坐标系取值：

- WGS-84 底图（OSM / Esri / OpenTopoMap）→ 用接口返回的 `lng_wgs84`；
  内置演示数据没有该字段时，用前端 `gcj02ToWgs84()` 三次迭代反算（误差 < 0.1 米）
- GCJ-02 底图（高德，仅作对照保留）→ 直接用 `lng`/`lat`
- 用户落点提交时同样跟随：WGS-84 底图上报 `coordinate: "wgs84"`，
  后端入库时统一转 GCJ-02 存储，保证数据口径不变

这样切底图不需要动数据库，"数据一套、展示多样"。

### 底图源清单（2026-10 实测可免 Key 直连）

| 源 | 坐标系 | 特点 | 商用注意 |
|---|---|---|---|
| OpenStreetMap 官方 | WGS-84 | 全球覆盖，中国偏远地区道路稀疏 | 用量政策禁止生产环境高流量使用 |
| Cyclosm（OSM 法国） | WGS-84 | 骑行/徒步路线友好 | 同 OSM |
| OpenTopoMap | WGS-84 | 等高线地形，户外场景好用 | 同 OSM |
| Esri World Imagery | WGS-84 | 卫星影像，分辨率高 | 需遵守 Esri 服务条款 |
| 高德（仅对照保留） | GCJ-02 | 国内 POI 最全 | 直连拼接不可商用，需官方授权 |

实测不可用（2026-10）：CARTO、Stadia Maps 已强制 API Key（免费档也要注册）。

## 三、四个技术难点

### 难点 1：坐标系（最容易翻车的地方）

国内有三套坐标系：

| 坐标系 | 使用者 | 说明 |
|---|---|---|
| WGS-84 | GPS 设备、手机定位、国际标准 | 未经加密的原始坐标 |
| GCJ-02 | 高德、腾讯、Google 中国区 | 国家强制加密，俗称"火星坐标" |
| BD-09 | 百度 | 在 GCJ-02 上再加密一层 |

**实测数据**：天安门参考点 WGS-84 `(116.3912757, 39.9074740)`，
转成 GCJ-02 后是 `(116.3975169, 39.9088753)`——**偏移 554.7 米**。

对一个"标记营地位置"的应用来说，偏 500 米意味着用户开车到荒地里去了。

工程上的处理策略：

1. **统一存储坐标系**：数据库里所有坐标一律存 GCJ-02，与底图对齐。
2. **入口转换**：手机 GPS / GPX 文件来源的数据（WGS-84）在入库时转成 GCJ-02。
3. **出口转换**：给接入百度 SDK 的第三方提供 BD-09 副本（接口里已经带上）。
4. **境内判断**：境外坐标不偏移，避免把国外营地也加偏。

代码见 `backend/geo.py`，往返转换误差实测 **0.0000 米**。

### 难点 2：视口查询与降采样

**绝不能**一次把全国营地拉给前端。做法：

- 前端每次 `moveend` / `zoomend` 带上当前 `bbox`（地图四角经纬度）
- 后端只查这个矩形内的点，走 `idx_spots_bbox` 复合索引
- 请求做 260ms 防抖，避免拖动时打爆后端

但光有 bbox 还不够：缩到全国视野时，bbox 几乎覆盖整个中国，仍有几万条。
所以按**缩放级别做地理网格抽样**：

```
zoom <= 6  ->  0.5°网格去重
zoom <= 8  ->  0.2°网格去重
zoom <= 9  ->  0.08°网格去重
zoom > 9   ->  全量返回（此时视野内数据量天然可控）
```

同一个网格内只保留排序最靠前的那条。这样低缩放级别下用户看到的是
"每个区域一个代表点"，放大地图后自动补全——体验上完全无感。

### 难点 3：UGC 质量（众包数据必然面对的问题）

三个机制叠加：

- **提交即待审**：`status=0`，人工审核后才 `status=1` 进入公众视野
- **评星 = 质量分**：`verify_score` 是 `ratings` 表中该营地星级均值
- **失效举报自动降级**：`verdict='stale'` 累计 3 次，营地自动回退到待审状态

防刷：同一用户对同一营地只能评一次（`UNIQUE(spot_id, user_id)`），
不能给自己提交的营地评分，300 米内同名营地禁止重复提交。

### 难点 4：会员门禁

不要在前端做隐藏——前端隐藏等于没隐藏。正确做法是**后端裁剪响应字段**：

```python
if is_member:
    d.update({"address": row["address"], "phone": row["phone"], ...})
else:
    d.update({"address": mask(row["address"]), "phone": "", ...})
```

免费用户拿到的 JSON 里 `phone` 就是空字符串，抓包也拿不到。
同时 `lng/lat` 保留精确值——因为点位本身是引流入口，
必须让免费用户看到"哪里有营地"，只是不知道"怎么联系"。

### 额外：瓦片防盗链

如果自建瓦片服务（而非直接用高德），参考 openmap.cc 的做法：
URL 带 `ticket`（账号级）+ `t`（瓦片级校验值）。
校验值 = `hash(ticket + x + y + z + 密钥)`，服务端验算，
防止别人把瓦片地址嵌到自己站里白嫖流量。

## 四、图片上传（UGC 平台的高危区）

图片上传是所有 UGC 平台最容易被打穿的地方。这里守四道关。

### 第一关：不信任何客户端提供的元数据

扩展名可以随手改，`Content-Type` 也是客户端填的。**唯一可靠的是文件内容本身。**

```python
ALLOWED_MAGIC = {
    b"\xff\xd8\xff": "jpg",           # JPEG
    b"\x89PNG\r\n\x1a\n": "png",      # PNG
    b"RIFF": "webp",                  # WebP（还需在第 8-12 字节校验 WEBP）
    b"GIF87a": "gif", b"GIF89a": "gif",
}
```

读文件头前 16 个字节比对魔数。把 `shell.php` 改成 `a.jpg` 上传？
第一关就被拦——它的头部是 `<?php`，不是任何图片的魔数。

### 第二关：丢弃客户端提供的文件名

```python
fname = f"{secrets.token_hex(12)}.{ext}"   # 完全重新生成
```

用户提交 `../../../../etc/passwd` 或 `a.jpg.php` 都无所谓——名字根本不用。
按日期分目录（`uploads/20261004/`）避免单目录塞进几十万个文件。

### 第三关：限制体积

```python
MAX_IMAGE_BYTES = 5 * 1024 * 1024
```

读完立即判断长度，超限直接中断，不把大文件留在内存里。

### 第四关：删除接口的路径校验

```python
safe = os.path.normpath(os.path.join(UPLOAD_DIR, path.replace("/uploads/", "")))
if not safe.startswith(os.path.realpath(UPLOAD_DIR)):
    raise HTTPException(400, "非法的文件路径")
```

删除接口是最容易遗忘的入口。`?path=../../etc/hosts` 这种请求必须被拦。

### 实测结果

`test_upload.py` 里的验证：

| 用例 | 结果 |
|---|---|
| PHP 木马改名成 `.jpg` | ✅ 拦截 |
| HTML 钓鱼页改名成 `.png` | ✅ 拦截 |
| 随机二进制改名成 `.jpg` | ✅ 拦截 |
| 空文件 | ✅ 拦截 |
| 6MB 文件 | ✅ 拦截（超 5MB） |
| 一次传 12 张 | ✅ 拦截（上限 8 张） |
| 文件名带 `../../../../` | ✅ 重命名为随机串 |
| 未登录上传 | ✅ 401 |
| 正常 PNG / JPEG / 多张混合 | ✅ 放行 |

### 生产环境还需要补的

1. **图片压缩与缩略图**：用户手机拍的图动辄 4MB，列表页加载原图会拖死页面。
   用 Pillow 生成 400px 缩略图，列表用缩略图，详情页才加载原图。
2. **剥离 EXIF**：手机照片的 EXIF 里带 **GPS 坐标**。用户上传营地照片，
   等于把自己到过的地方全暴露了。必须在上传时剥离 EXIF。
3. **迁移到对象存储**：本地磁盘不适合生产环境（没法水平扩展、备份麻烦）。
   阿里云 OSS / 腾讯云 COS + CDN。
4. **人工审核**：图片内容也必须进审核队列。用户可能上传违规内容，
   平台对此负有审核义务。
5. **接口限流**：防止有人用脚本刷上传占满磁盘。

## 五、管理后台的权限隔离

后台是**独立的页面**（`admin.html`），与用户端完全分离。共用同一套 API，
但后台接口全部走 `/api/admin/*` 前缀，并依赖 `require_admin`：

```python
def require_admin(user=Depends(require_user)):
    if not user["is_admin"]:
        raise HTTPException(403, "需要管理员权限")
    return user
```

**关键是后端必须校验，前端按钮隐藏只是体验优化。** 实测普通用户的 token
访问 5 个后台接口全部返回 403，未登录返回 401。

### 字段白名单

后台的 `PATCH` 接口不能变成"万能改表"入口：

```python
editable = {"name", "lng", "lat", "province", "city", "spot_type",
            "address", "phone", "price_range", "detail"}
```

白名单之外的字段（`created_by`、`verify_score`、`is_admin`）直接忽略。
实测提交这些字段会返回"没有可更新的字段"，数据不被篡改。

### 操作日志

后台每个写操作都写 `audit_log`：谁、什么时候、对哪条数据、做了什么。
这是责任追溯的基础，尤其是多管理员协作时。

### 生产环境补充

- **二次验证（2FA）**：管理员账号是最高价值目标，光靠密码不够
- **IP 白名单**：后台限制在公司网络或固定 IP 访问
- **登录失败锁定**：连续失败 N 次锁定账号
- **独立的登录入口**：不要暴露 `/admin` 路径，改成随机后缀

## 六、数据模型

```
users ──┬── spots ──── ratings
        ├── point_logs
        ├── orders
        └── tokens
```

核心字段说明：

- `spots.status`：0 待审 / 1 通过 / 2 驳回 / 3 失效
- `spots.facilities`：JSON 数组字符串，避免为多对多关系单独建表
- `spots.verify_score`：冗余字段，每次评分后重算并落库，避免列表页做聚合查询
- `orders.amount_fen`：**金额单位用分**，绝不使用浮点数存钱
- `audit_log`：记录管理员的每次操作，用于责任追溯

## 八、部署建议

**最小可用（单机）**

```
云服务器 2核4G（约 60-100 元/月）
├── Nginx      静态资源 + 反代 + HTTPS
├── uvicorn    2 个 worker
└── SQLite     单文件，每 6 小时备份一次
```

**上量后（10 万 POI 以上）**

1. SQLite → PostgreSQL + PostGIS（用 `ST_DWithin` 做真·空间查询）
2. 加 Redis 缓存热点 bbox 的查询结果，TTL 5 分钟
3. 图片存储迁到对象存储（OSS/COS），不要放本地磁盘
4. 瓦片如果自建，用 nginx `proxy_cache` 做本地缓存，命中率能到 90%+

**成本估算**

| 项目 | 月成本 |
|---|---|
| 服务器 | 60-100 元 |
| 地图瓦片（高德商用授权） | 视量级，**这是最大变量** |
| 对象存储 + CDN | 20-50 元 |
| 域名 + HTTPS | 5 元 |

要保本，按 99 元/三年计算，需要约 **50-100 个会员** 覆盖前两项基础成本。

## 九、地图服务授权（成本与风险的关键项）

这是**最容易被忽略、也最容易出事**的一环：

- **高德/腾讯瓦片**：不能直接拼接商用。需要申请「地图 API 商用授权」，
  按调用量计费。个人学习可用，商业运营必须授权。
- **天地图**：国家测绘局官方服务，有免费额度，控制台申请 Key 即可，
  商用需按其条款申请。**推荐作为低成本起步方案**。
- **自建瓦片**：用 OpenStreetMap 数据 + `openstreetmap-tile-server` 自渲染，
  完全自主可控，但需要一台至少 8G 内存的机器跑渲染，且 OSM 数据在国内
  某些区域精度不如高德。
- **OSM 公共瓦片**：`tile.openstreetmap.org` **明确禁止**用于生产环境的高流量场景，
  不要图省事直接挂上去。

代码里默认用的是高德免 Key 瓦片，**仅供开发调试**，上线前必须替换。

## 十、密钥登录（匿名令牌账号）

这是可选的一种登录方式，参考了桃花缘那类站点的设计：**不注册用户名密码，
直接发一串 32 位密钥当账号用**。

### 它到底是什么

本质上是把 `Bearer Token` 直接交给用户长期持有。传统做法是
"账号 + 密码 → 登录 → 换取短期 token"，这个做法是**把长期凭证本身当账号**，
省掉登录这一步的分层。

**一句话说清代价**：用户体验极简（点一下就有一个账号），
代价是**凭证即账号，丢了就没了**。

### 密钥设计

```python
KEY_ALPHABET = "ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz23456789"
KEY_LENGTH = 32
```

- **58 个字符**：去掉了 `0O`、`1lI` 这些抄写时容易看错的字符（这点很重要，
  用户会截图保存、手抄，一个字符看不清就废了）
- **32 位长度**：空间是 58³² ≈ 2¹⁸⁷。对比一下，地球上的原子总数约 2¹⁶⁶——
  暴力枚举在物理上不可行
- **显示格式**：`XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX`，便于核对和抄写

### 存储：为什么只存哈希

```python
def hash_secret_key(key):
    return hashlib.sha256((PEPPER + normalize(key)).encode()).hexdigest()
```

| 做法 | 脱库后果 |
|---|---|
| 存明文 | 攻击者拿到全部用户账号，直接登录 |
| 存 sha256(key) | 32 位随机串无法反推，但可以用彩虹表 |
| **存 sha256(PEPPER + key)** | 没有 PEPPER 就无法离线爆破。✅ |

**这里刻意用快哈希（sha256）而不是 PBKDF2**，理由是：
PBKDF2 / bcrypt 这类慢哈希是为了抵抗**低熵密码**的字典攻击。
而 32 位随机密钥的熵极高，字典攻击不成立，慢哈希只会白白浪费 CPU。
这是"慢哈希不适用于高熵凭证"的典型场景。

`PEPPER` 必须从环境变量注入，绝不能硬编码进仓库。

### 容错处理

用户会从聊天记录、截图里复制密钥，格式必然混乱。所以输入时做归一化：

```python
def normalize_key(key):
    return "".join(ch for ch in key if ch not in " -_")
```

实测通过的格式：带连字符、无分隔、前后有空格、下划线分隔。
**但大小写不能容错**——字符集同时含大小写，如果做成大小写不敏感，
密钥空间会从 58³² 降到约 33³²，凭空少了一大截熵。

### 关键的取舍：不提供找回

服务端只存哈希，所以**无法找回**。这是这个模式必须接受的代价，
不能靠"再存一份明文"来解决——那就等于把最大的安全优势扔掉了。

替代方案（代码里实现了前两条）：

1. **领取时强制显式保存**：弹出密钥卡片，提供「复制」和「下载 txt 卡片」
2. **只显示末 4 位供核对**：`key_preview` 字段，让用户确认"这是我的密钥"
3. **支持换发**：怀疑泄露时点一下就换新密钥，旧密钥立即失效
4. 付费用户在订单里有联系方式，客服可人工核验后重签

### 为什么这个设计对某些场景是合理的

**优点**
- 注册转化率极高：点一下就完事，没有任何表单
- 无手机号 / 邮箱收集，天然规避个人信息保护合规问题
- 服务端不需要处理密码重置、短信验证码等一堆麻烦事

**缺点与风险**
- 用户丢失凭证就永久失去账号（含已付费的会员和积分）
- 用户容易在群聊里分享密钥（截图传播是必然的）
- 无法主动联系用户（没有联系方式），运营触达为零
- 换设备要手动输入 32 位字符，体验较差

**结论**：适合"低价值匿名账号"场景，比如游客试用、临时身份。
**如果用户会付费，强烈建议同时提供绑定手机号/邮箱的选项**——
否则用户付了 99 元然后丢了密钥，客服纠纷会非常多。
代码里 `users` 表已经预留了 `username` 字段（可空），
匿名账号后续可以升级绑定，两套登录方式能共存。
